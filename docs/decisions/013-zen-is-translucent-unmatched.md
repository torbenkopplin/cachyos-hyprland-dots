# 013 — Zen is translucent, and nothing here tries to make it match

**Settled against matching on 2026-08-19.** Status: in force.

`browsers/zen/user.js` sets `zen.widget.linux.transparency` and
`browser.tabs.allow_transparent_browser` to true. The "transparent zen" mod and
the "Zen Internet" extension are installed *inside* Zen, which no file in this
repo can do. `user.js` is read only at startup, so a restart is what applies it.

No other browser is translucent, which is the "either none at all, or only where
an extension takes effect" half of the original ask, and that part is satisfied.

**What was dropped is the *match*.** There is no `browser` level in `glass.conf`,
no generated stylesheet, and nothing measures whether Zen looks like kitty. It is
translucent at whatever the mod paints.

## What was built first, and why it went

A `browser` level written into a generated Zen stylesheet. It measured correct and
looked wrong to use. Three reasons, and the first is the one that matters:

1. **The tint only ever showed on pages that paint no background of their own,**
   and almost none do. Measured 2026-08-19 with `noct-check browser-glass`: all
   four browsers composited at 0.85, 0.00 apart, on an ordinary page. So the
   effect was worth far less than the config made it look.
2. **It needed a specificity fight with somebody else's extension.** The mod
   paints `.browserStack > browser` `!important` from
   `:root:has([mod-sameerasw_zen_light_tint="1"]) …`, specificity 0-3-1 against
   0-2-1 — so the page kept the mod's 10% wash and measured an own alpha of 0.
   It was beatable with `#main-window …` (1-1-1) plus a tripled `:root` (0-4-1),
   and winning that fight silently, every time the mod changes its selector, is
   not a thing to build on.
3. **There was no room between the two states.** The 0.06 focus step left nothing
   between "indistinguishable from a window" and "looks like a window in the other
   focus state", which is the ground the effect had to stand on. (That step is
   itself gone now, at `inactive_opacity = 1.0` — see
   [010](010-glass-is-the-terminal-only.md).)

**If the matching ever comes back**, the thing to fix first is not the number. It
is that the effect depended on four parts nobody here owns — a mod, an extension
and two prefs — all read once at startup. Anything rebuilt on that fails the same
way. Two of the four are in play again now that the transparency is back on, which
is why the mod looking broken has a documented cause rather than a debug session.

## The parity gate went with it

`noct-check browser-glass` used to fail when the four browsers were more than 0.06
apart. A deliberately translucent Zen *is* exactly that, so the gate could only
fire on the intended state. It was **retired rather than exempted**, and not kept
as a metric either — a baseline tolerance is the same gate under another name.

It still fails on the three real faults: more opaque than the compositor allows,
**any browser but Zen** under it, or page text below 4.5:1. That middle one is
what keeps the other three effect-free.

## One thing to clean up on an older machine

Any machine that ran this repo before 2026-08-19 has the stylesheet `noct-glass`
used to generate. Nothing writes it now, and Zen would go on reading it:

```sh
grep -lZ "Generated by noct-glass" ~/.config/zen/*/chrome/userChrome.css | xargs -0 -r rm -v
```

`-Z`/`-0` are load-bearing. Zen's profile directories have spaces in their names
(`bxz0cb9y.Default Profile`), so a plain `grep -l | xargs rm` splits every path in
two and each `rm` fails with "No such file or directory" — which reads exactly
like "there was nothing to remove". That is why this machine was recorded as
already clean while both files were still there.

Full reasoning: [theming.md](../theming.md#what-was-tried-with-zen-and-dropped).
